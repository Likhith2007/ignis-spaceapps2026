TRANSMISSION 006 // STRATEGIC UPDATE
What Changed, What Survives

The mission is unchanged. The way of working is rebuilt from the keel up.

REV 1 of this campaign assumed a team of two to four builders with a pre-built Next.js chassis, a registry of locally-served Hugging Face models, and FastAPI micro-services gluing the stack together. The operating reality is now different and sharper: one operator, with frontier AI assistants available only as chat — ChatGPT, Astra, Gemini, Claude — and nothing resident on the machine. There is no local model serving, no long-lived agent, no GPU, and no background daemon. Everything that must run, must run somewhere else: inside GitHub Actions, on a hosting platform’s edge, or behind a public API that returns an answer in a single request.

This constraint sounds like a downgrade. It is not. It is a forcing function toward the strongest possible build style: deterministic science computed in continuous integration, data products frozen as static JSON, a front-end that is pure static hosting, alerts delivered by bots instead of back-ends, and every creative inference done either at build time or through a free-tier hosted API. The result is an app that cannot crash in the demo because there is almost nothing left to crash — and an operator whose only job during the 48 hours is to direct chat assistants, accept their work at acceptance gates, and commit. This document defines that way of working; its companion, SP-2026-007, converts it into a portion-by-portion build bible for PYROCHRON, the flagship challenge.

SECTION 01 // THE CHAT-ONLY CONSTRAINT MODEL
One Human, Many Minds, One Interface

Define the constraint precisely, then exploit it precisely.

The tooling reality has three hard edges. First, AI is conversational: the assistants are brilliant at writing, reviewing, and debugging code, but they do not persist between sessions, cannot hold the build running, and cannot watch the world. Second, there is no local heavy compute: no GPU inference, no SAR processing farm, no model fine-tuning, nothing that would take longer than a laptop tolerates. Third, the operator is a single thread of attention: unlike a four-person team, one human cannot simultaneously debug an ingestion script, style a component, and write a pitch. Every REV 2 decision follows from trading against these three edges — and the trade is always the same: move work to machines that never sleep (CI schedulers, static CDNs, hosted APIs), and reserve the human for judgment, sequencing, and taste.

The model also has a generous upside the old plan never used: frontier chat assistants are outstanding at exactly the work this build needs. FIRMS CSV ingestion, climatology statistics, React components, GitHub Actions YAML — this is well-trodden, heavily-documented territory where chat-generated code is near-expert quality on the first or second iteration. The tasks that killed REV 1’s most ambitious alternates — SAR interferometry, asteroid difference imaging, on-device vision models — are precisely the tasks that get harder under this constraint, which is why the re-selection verdict in Section 02 reshuffles the bench. The constraint does not just change how we build; it sharpens what we should build.

02.2 The Verdict, Re-Confirmed and Strengthened

The headline of the re-score is that the constraint change widens the flagship’s lead. PYROCHRON was already rank 1 at 8.30 under team assumptions; under solo-plus-chat it stretches to 8.80 because every one of its inputs arrives as a plain HTTP request, every one of its computations is a scheduled Python script, and none of its science requires a GPU or a served model. The distance to the field is no longer a matter of taste — it is structural. 03.1 Layer A — The Chat-Only Coding Protocol

Chat assistants have no memory of the repo, so the protocol manufactures memory out of small context and hard artifacts. Work is decomposed into task cards: a single file or single function with a stated input, output, and acceptance test, small enough that its entire context fits in one message. Each prompt carries three things — the relevant file (pasted, not described), the exact acceptance command, and the constraint list (fonts, library versions, style rules). The assistant returns code; the operator runs the acceptance command locally or pushes to CI; failures go back to the same chat with the verbatim error text pasted. One loop per task card, then commit with a conventional message. The commit history is the project’s real memory: any fresh chat can be onboarded in thirty seconds with git log --oneline plus the file in question.

Because the operator can hold several chat tabs open, the solo build runs as three standing sessions with strict jurisdictions. The DATA session owns everything under scripts/ and .github/workflows/; the FRONTEND session owns the app directory; the QA session owns issues, docs, and the submission kit. Sessions never edit each other’s files — cross-cutting requests are filed as GitHub issues (via the GitHub MCP or plain web) and picked up by the owning session. This recreates the old team’s code-review benefit at zero personnel cost: before any merge, the operator asks a second, different assistant to review the diff in its own window; reviewers catch hallucinated API parameters more often than any linter. That two-assistant pattern — one writes, one critiques — is the single highest-value habit in this document.

Task card rule. One file or one function per prompt; input, output, and acceptance command stated up front. If the card needs two paragraphs of context, split the card.
Error-paste rule. Never paraphrase an error. Paste the verbatim stack trace plus the line of code that produced it; assistants fix real errors faster than descriptions.
Reviewer rule. Every non-trivial diff gets a critique pass in a different assistant’s window before merge. Author-assistant and reviewer-assistant must not be the same model.
Commit rule. Commit after every green acceptance test, message format P{n}: {what} — {proof}. The log doubles as the methodology page for judges.
03.2 Layer B — The MCP Toolbridge

Model Context Protocol servers are what turn a chat window into an operator console, and three of them cover the entire build. The GitHub MCP server (official, remote) exposes toolsets for Repos, Issues, Pull Requests, Actions, and Discussions — which means the operator can create the repo, file task cards as issues, push branches, open PRs, and read workflow logs without leaving the chat that is writing the code. The Playwright MCP server gives the QA session eyes: it navigates the deployed preview, captures structured accessibility snapshots, and takes screenshots on demand — that is how a solo operator runs a visual regression pass and proves console-clean rendering at 2 a.m. The fetch MCP probes data endpoints directly from chat — paste a FIRMS URL, get the first rows back, confirm the schema before writing a line of ingestion code.

The bridge also has a fallback mode, because hackathon Wi-Fi and tool outages are part of the game. If MCP is unavailable, every action it enables has a CLI equivalent the assistant can generate verbatim: gh commands for repo and workflow operations, curl for endpoint probes, and a fifteen-line Playwright script for screenshots. The protocol is identical — only the transport changes — and the bible in SP-2026-007 writes the fallback commands next to every MCP step so no decision ever waits on a tool.

WHY MCP MATTERS SOLO
A team loses one member’s hour to tool friction and absorbs it. A solo operator loses the same hour with no one to absorb it. MCP exists in this doctrine to keep the operator’s hands on judgment — the round trip from “idea” to “merged and deployed” must stay under ten minutes all weekend.
03.3 Layer C — Automation and the $0 Cloud

Everything that must run, runs in GitHub Actions — free on a public repository, which the build adopts deliberately (see Section 05 for the secrets hygiene that makes a public repo safe). Three workflows carry the entire operation: ingest (scheduled, pulls FIRMS NRT every six hours and appends to the archive), build-products (recomputes harmonized JSON products on every ingest and commits them), and deploy (static export to Vercel or Netlify on every commit to main, with preview URLs per branch). Alerts ride out through the Telegram Bot API and Resend free tier — a daily fire digest and threshold alarms, both initiated by Actions, both needing zero infrastructure. Optional hosted inference, if any feature wants it, rides the Hugging Face Inference Providers free tier (a few hundred requests per hour, models under roughly 10B parameters) — useful for a demo flourish, forbidden in the critical path.

The total infrastructure bill is zero dollars, and more importantly the operational surface is a handful of YAML files the operator can read in one sitting. Every moving part is observable in a public place: workflow runs are browsable, artifacts are downloadable, and a judge who wants to check honesty can replay the whole pipeline from the repository. This transparency is not a consolation prize for lacking a back-end — it is the Best-Use-of-Data pitch itself.

SECTION 04 // MODEL STRATEGY REV 2
From Model Registry to Method Registry

Every REV 1 model task gets a deterministic substitute or a hosted one-shot — nothing in the critical path needs weights we own.

REV 1’s AI division assumed a local Hugging Face registry: Chronos-Bolt for forecast, Prithvi-EO for downstream Earth observation, an embedding model for retrieval, an LLM service for briefing generation. Under the chat-only constraint that entire registry is retired — and the honest engineering answer is that the flagship never needed it. The scientific work judges reward in the fire brief is calibration and climatology arithmetic: z-scores against a 20-year baseline, seasonal decomposition, a transfer function between two sensors. That is a hundred lines of NumPy, fully reproducible in CI, and more defensible in front of a judge than a black-box forecast. Models return only where they add demonstrable value at zero operational risk: build-time narrative generation and an optional hosted forecast flourish.

SECTION 05 // INFRASTRUCTURE DECISIONS
Public Repo, Static Products, Zero Dollars

Five decisions made now so that no hour of the event is spent making them.

Decision 1 — the repository is public. Scheduled GitHub Actions workflows do not run on private repositories under the free plan, and the entire automation layer depends on cron; a public repo also gives judges the replayable-pipeline transparency described above. The cost is secret hygiene: MAP_KEY, Telegram token, and Resend key live only in encrypted Actions secrets, never in client code, never in logs, and the NRT proxy reads its key server-side so the browser never sees one. Decision 2 — scheduling belongs to Actions, not the host. Hosting-platform cron on free tiers is limited and opaque; the build uses Actions for every schedule and a deploy hook for publication, so the pipeline and the schedule live in the same reviewable YAML.

Decision 3 — data products are static JSON committed to the repo. Each product file stays under 5 MB and the full set under 40 MB, which keeps git fast, deploys instant, and the app entirely CDN-served; size budgets are enforced by the build script so no portion can silently bloat the repo. Decision 4 — the front-end is a static export (Next.js static export or Vite) with exactly one serverless function for live NRT passthrough — deployable to Vercel or Netlify hobby plans with preview URLs per branch, which is what the Playwright QA loop tests against. Decision 5 — every external call has a static fallback: basemap tiles from GIBS fail gracefully to a plain dark style, the live proxy fails to the last committed product, and the demo script never depends on a fresh API response. The cumulative result is a submission whose failure surface is close to zero and whose running cost is exactly zero.

SECTION 06 // THE SOLO OPERATING RHYTHM
Managing One Body, Three Chats, Forty-Eight Hours

Solo execution fails by energy collapse before it fails by engineering. The rhythm is the plan.

A four-person team survives 48 hours by rotating exhaustion; a solo operator survives by banking sleep in advance and defending two hard blocks — roughly six hours in each night, non-negotiable, because hour 36 of uninterrupted work produces negative output. Between blocks, the operator works in 90-minute focus cycles against one session at a time, with the other two chats parked on long-running requests (a component build, a workflow run, a QA sweep) whose results are waiting at pickup. The commit cadence is the metronome: no 90-minute cycle ends without a green acceptance test and a push, so CI is always proving the last claim. If a cycle ends red, the rule is to revert to the last green commit and re-ask with a tighter prompt — never to debug past the second failed iteration in the same window.

Decision-making adapts to the missing team vote through hard default rules written now, while calm. Challenge commitment happens at the Hour 2 data check and only if a data check fails does the default order advance (PYROCHRON → PULSE → ROOTLOGIC); no swap is legal after Hour 2 under any circumstance. Scope disputes between the operator’s enthusiasm and the plan are settled by the plan — the bible’s portion list is the scope, and new ideas go into a parking-lot.md file rather than the build. The only metric that matters at every gate is: could a judge demo this in 90 seconds right now? Portion ordering guarantees the answer is yes from Hour 24 onward, which is what makes the final polish cycles calm instead of desperate.
