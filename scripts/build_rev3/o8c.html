SECTION 03 // VAULT & DATA-FLOW ARCHITECTURE
Where Secrets Live, Where Data Flows

One private source of truth, encrypted at the runtime layer, zero keys in anything a judge will ever see.

The vault repository Hisernberg/spaceapps-2026-vault (private, created 2026-09-20, HTTP 201) is now the single canonical home for credentials and automation scripts. It contains secrets.env with all live values, placeholder-only secrets.env.example for public use, the three production pull scripts, the verification report with all recorded evidence, and the workflow definitions. Three Actions secrets were installed via the encrypted-seal API (all HTTP 201): FIRMS_MAP_KEY, NASA_API_KEY, and HF_TOKEN. A second private store exists at huggingface.co/datasets/Nabidnur/spaceapps26-data for files too large for git, readable by automation only. This two-store layout means a public project repository can run scheduled automation without ever containing a plaintext secret.

WHY CRON LIVES IN THE PUBLIC REPO
On the GitHub free plan, scheduled workflows only run on public repositories — a constraint already captured in REV 2 doctrine. The vault (private) therefore holds canonical scripts and secrets, while the public project repo holds the cron. The key exists there only as an encrypted Actions secret, set once with gh secret set or the seal-box API. Push-triggered workflows do run on private repos, which is why the vault’s own verification workflow works today.
